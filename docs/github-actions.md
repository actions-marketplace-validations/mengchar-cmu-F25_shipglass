# Compare releases in GitHub Actions

Shipglass compares two archive files already on the runner, adds a compact job summary, and saves an interactive HTML report plus JSON and Markdown as a workflow artifact. Your workflow chooses how to build or download the baseline and current archives.

```yaml
- name: Compare release archives
  id: shipglass
  uses: mengchar-cmu-F25/shipglass@v0.3.2
  with:
    before: dist/before.tgz
    after: dist/after.tgz
    max-growth-bytes: '1000000'
```

Place this step after the steps that produce both files. Paths are resolved from the job's current working directory, normally the checked-out repository, rather than from the Shipglass Action's directory. Absolute paths also work. Inputs are local paths, not URLs, registry versions, or glob patterns.

## Complete workflow

This example is for a repository that already contains two release archives. Save it as `.github/workflows/release-diff.yml` on your default branch, run it from the Actions tab, and enter the two repository-relative paths. Checkout retrieves the caller's repository; the Action uses its own bundled code.

```yaml
name: Compare release archives

on:
  workflow_dispatch:
    inputs:
      before:
        description: Baseline archive path in this repository
        required: true
        type: string
      after:
        description: Current archive path in this repository
        required: true
        type: string

permissions:
  contents: read

jobs:
  compare:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Compare release archives
        id: shipglass
        uses: mengchar-cmu-F25/shipglass@v0.3.2
        with:
          before: ${{ inputs.before }}
          after: ${{ inputs.after }}
          max-growth-bytes: '1000000'
```

For a build pipeline, replace the manual inputs with paths produced by your earlier build or download steps. The Action does not select a baseline, fetch packages, or run a package manager. If using `npm pack --ignore-scripts`, first run the build your package requires: disabling lifecycle scripts also skips output normally generated by `prepack`.

For a runnable example that creates its own synthetic archives, see Shipglass's [Action integration workflow](../.github/workflows/action.yml) and [workflow runs](https://github.com/mengchar-cmu-F25/shipglass/actions/workflows/action.yml).

To compare two published npm versions directly, use the [manual npm workflow](npm.md#run-in-github-actions). It prepares Python and runs the CLI with package and version inputs, then saves the same report formats.

## Review a Python wheel before release

Shipglass's own [test workflow](../.github/workflows/ci.yml) builds a wheel, installs that same wheel for its tests, then compares it with the explicitly selected `v0.3.2` release. The Ubuntu/Python 3.12 job saves a `shipglass-wheel-diff` artifact and summary on every push and pull request. It uses the existing build, without a second build or an optional failure threshold.

For a Python project that produces one wheel, add these steps after checkout and Python setup. Replace the baseline URL with your project's previously published wheel:

```yaml
- name: Build candidate wheel
  run: python -m pip wheel --no-deps --wheel-dir dist/candidate .

- name: Download the selected baseline
  run: |
    curl --fail --location --output dist/baseline.whl \
      https://github.com/mengchar-cmu-F25/shipglass/releases/download/v0.3.2/shipglass-0.3.2-py3-none-any.whl
    cp dist/candidate/*.whl dist/candidate.whl

- name: Compare wheel contents
  uses: mengchar-cmu-F25/shipglass@v0.3.2
  with:
    before: dist/baseline.whl
    after: dist/candidate.whl
    artifact-name: wheel-diff
```

This snippet uses an Ubuntu runner. Use a clean output directory and select one matching wheel for each baseline/candidate pair; projects producing multiple platform wheels need one comparison per pair. The renamed copies distinguish the archives in the report. Keep the original wheel filenames when installing them.

The baseline is an explicit release, not a rebuild or an automatically selected latest version. Update it when you want reviews to compare against a newer release. Version changes rename a wheel's `.dist-info` directory, so those metadata entries appear as added and removed. A README change can also change `METADATA` when the README supplies the package description.

## Read the result

Open the workflow run's job summary for sizes, file counts, up to ten changed paths, and up to ten current-release cautions. The summary orders changed paths by absolute size change and also counts content changes with no size difference. The downloadable artifact contains:

- `report.html`: the full interactive report; download and open it locally in a browser.
- `report.json`: the full structured comparison.
- `report.md`: the compact Markdown summary.

The job summary includes a download link. GitHub requires sign-in and access to the repository to download the artifact, including for public repositories. The link stops working when the artifact expires or the artifact, run, or repository is deleted. See [GitHub's artifact output documentation](https://github.com/actions/upload-artifact#outputs).

## Inputs

| Input | Default | Meaning |
| --- | --- | --- |
| `before` | Required | Local path to the baseline archive. |
| `after` | Required | Local path to the current archive. |
| `max-growth-bytes` | Empty; disabled | Fail if expanded payload growth exceeds this non-negative integer. Equality passes. Compressed archive size does not control this check. |
| `fail-on-warnings` | `'false'` | Set to `'true'` to fail on any packaging caution in the current archive. Removing a cautioned file does not fail this check. |
| `strip-components` | `'0'` | Remove this many leading path components from both archives. Entries with too few components are omitted. |
| `artifact-name` | Automatically generated | A distinct name for each comparison. If you set one, make it unique across steps and matrix jobs in the workflow run. |

Supported archives and scanning limits are the same as the [CLI](../README.md#compare-what-you-ship). Use `strip-components: '1'` when both archives have a wrapper directory that should be excluded from path matching. This also omits top-level files; Shipglass never chooses prefixes automatically.

Both blocking checks are optional. When a configured check fails, the Action writes the summary, uploads the reports, and then fails the step. Invalid options, missing files, and malformed or unsupported archives fail before uploading an artifact. An artifact upload error also fails the step.

## Outputs

Assign an `id` to the step and read outputs through `${{ steps.shipglass.outputs.<name> }}`.

| Output | Meaning |
| --- | --- |
| `artifact-url` | GitHub download URL for the three reports. Requires sign-in. |
| `report-path` | Absolute HTML report path on the runner. |
| `json-path` | Absolute JSON report path on the runner. |
| `markdown-path` | Absolute Markdown summary path on the runner. |
| `delta-bytes` | Signed change in expanded payload size, in bytes. |
| `warning-count` | Number of packaging cautions in the current archive. |
| `check-result` | `passed` or `failed` for configured checks; empty when no comparison could be produced. |

`passed` means no configured policy was violated; it does not mean no warnings exist. If you intentionally inspect outputs after a failed policy check, use `continue-on-error: true` on the comparison step and inspect its `outcome` along with `check-result`. Reports saved after a failed policy check remain available in the workflow run.

## Runtime and privacy

The composite Action prepares Python 3.12 with `actions/setup-python@v6` and `update-environment: false`, then invokes Shipglass's bundled code directly. It does not install packages with pip or replace the caller's Python selection on `PATH`. Python setup may download an interpreter if the runner does not already cache it. The comparison itself reads local archives and never executes their scripts or extracts their contents into the project.

Only the generated HTML, JSON, and Markdown reports are uploaded to GitHub. The input archives are not uploaded by this Action. Reports exclude archived file contents, but filenames, sizes, and other metadata can reveal private information. JSON includes content hashes; HTML and Markdown omit them. All three formats omit link targets. The job summary also exposes paths and metadata to people with access to that run. Use repository access and artifact retention settings appropriate for your archives. The standalone CLI uploads nothing; its local-file commands run offline, while the optional [`npm`](npm.md) and [`pypi`](pypi.md) commands download public packages.

The [integration workflow](../.github/workflows/action.yml) runs on GitHub-hosted Linux, macOS, and Windows. Self-hosted runners need Bash and a runner version compatible with the dependencies' Node 24 runtime. `setup-python@v6` documents a minimum runner version of v2.327.1; see its [runtime requirements](https://github.com/actions/setup-python#breaking-changes-in-v6).

This Action uses `actions/upload-artifact@v7`. GitHub documents that `upload-artifact@v4+` is [unsupported on GitHub Enterprise Server](https://github.com/actions/upload-artifact#ghes-support). On GHES, run the CLI instead and upload its output with your server's supported artifact mechanism:

```sh
shipglass compare before.tgz after.tgz \
  --output report.html --json report.json --markdown report.md
```

Install the CLI as described in the [README](../README.md#try-it). If you enable CLI blocking checks, configure your upload step to run after exit code 1 so reviewers still receive the reports.
